# kelyra 语言目标基线 v0.1

状态：设计草案，尚未实现。日期：2026-09-16。

本文保留用户提出的七项核心方向：依赖管理、跨平台、高性能、C 与汇编、AI 友好、图形学与 Shader、多线程。新增“内存与资源安全”作为共同基础。平台顺序、性能门槛和具体技术路线均为建议，不能视作用户已确认的实现承诺。

## 1. 产品目标与边界

开发一门默认安全、性能可预测、支持 CPU 原生程序与 GPU Shader、能接入 C 生态，并适合人和 AI 共同维护的系统编程语言及配套工具链。

目标交付物包括语言规范、编译器、基础标准库、包与构建工具、诊断和语义查询接口、调试支持、Shader 编译与绑定工具，以及可以复现的验收项目。

第一版应在全部七项方向上形成可运行的最小实现。特性的存在必须由实际程序验证，不能只用关键字、空接口或命令占位符证明。

初始边界：

- 支持局部替换现有 C/C++ 项目中的模块。完整 C++ 模板、继承、异常及 ABI 互操作不作为首版要求；C++ 库可通过明确的 C 包装层接入。
- 首版不承诺所有操作系统、CPU 和 GPU 都可用，也不承诺任意主机都能交叉构建任意目标。
- 不要求自研汇编器、链接器、GPU 驱动、完整图形引擎或公共包托管服务。可以复用并固定成熟组件的版本。
- 源码、契约、诊断及修改记录必须便于人类阅读和审查。

## 2. 共同基础：内存、资源与错误语义

必须具备：

- 使用普通原始指针 `*T`、取地址 `&value` 和解引用 `*pointer`；不引入借用、生命周期或 `unsafe` 边界。
- 指针访问、资源释放和并发同步的正确性由程序员及库负责；调试构建可以提供可选的动态检查。
- 明确标准库分配器和资源释放 API，不把所有权编码进指针类型。
- 不强制依赖追踪式 GC。引用计数、arena 和线程池等机制的启用及成本必须可辨识。
- Release 构建遵守语言定义的检查级别，不因优化改变已启用检查的行为。
- 为整数溢出、失败返回、panic/trap、析构和取消制定明确语义。程序错误不得静默伪装成成功值。
- C 调用、裸指针、汇编及原始 GPU 操作直接可用，并具有明确的 ABI 和行为文档。

GPU 需要单独定义地址空间、访问权限、越界行为、同步与资源存活规则；不得宣称任意 Shader 都无数据竞争。

不承诺：编译通过即业务正确、无死锁、无资源泄漏，或不受外部库缺陷影响。验收同时需要规范审查、应拒绝的反例、运行检查和测试；有限测试不能证明整个编译器实现健全。

## 3. 七项必须完成的目标

### G1：依赖管理与构建

必须能力：

1. 单一项目清单和统一命令入口，覆盖依赖解析、构建、测试、格式化、文档、运行及打包。
2. 支持本地路径、固定 Git 提交和不可变归档依赖；记录传递依赖、内容摘要、特性和来源。公共 registry 可以后置。
3. 锁文件之外，记录编译器、标准库、链接器、C 工具链、Shader 工具链、目标三元组、CPU/GPU 能力和构建选项。
4. 区分运行于构建主机的生成工具与运行于目标平台的程序，正确处理交叉编译依赖。
5. 提供固定依赖构建、预取、离线构建、依赖解释和冲突诊断；所有必要内容已准备好时离线构建不应访问网络。
6. 将 C 源码、C 库、汇编文件和 Shader 纳入同一个依赖图。二进制缓存键覆盖 ABI、目标特性、SDK、选项及输入内容。
7. 默认使用声明式构建。必须执行的生成程序声明输入、输出、工具版本和环境需求；不能把未声明的网络或主机状态当作可复现输入。

验收：一个包含本语言库、C 库、汇编、Shader 和代码生成步骤的项目，在两套干净的受支持环境中按记录的输入完成构建。预取完整后可以断网重建。修改锁文件要求之外的解析结果必须失败并解释原因。

可复现性分层：先保证依赖与工具链可重建；再对固定目标和工具链、已归一化时间与路径的指定产物验证字节一致。不同 OS/架构生成的二进制不要求相同，签名和部署包单独定义。

### G2：跨平台

必须能力：

- 显式描述 OS、架构、ABI、CPU 特性、最低系统版本及可用标准库层级。
- 区分可以生成代码、可以链接、可以运行、具有 CI 和维护承诺的支持级别。
- 提供无 OS 依赖的核心层、可选分配层和 OS 标准库层。设计兼容 freestanding，不要求首版提供完整裸机生态。
- 统一常见文件、时间、线程和动态库接口；对文件路径、编码、权限和系统错误等差异作明确约定。
- 用能力检查表达平台特性。错误的目标或缺失的 SDK、原子操作、指令特性必须获得早期诊断。

建议平台路线：

| 阶段 | CPU 运行目标 | 图形运行目标 | 支持要求 |
| --- | --- | --- | --- |
| M0 原型 | Linux x86-64 | 可进行离线 Shader 编译 | 不宣称完成跨平台 |
| M1 首版闭环 | Linux x86-64、Windows x86-64 | 两个平台上的 Vulkan 基础能力集合 | 原生构建运行；另外验证一条声明清楚的交叉编译路径 |
| M2 扩展 | Linux AArch64、macOS AArch64 | 增加 Metal；按需求增加 D3D12 | 真机运行，明确每个后端的能力差异 |
| M3 后续 | RISC-V 64、Wasm、移动端或 freestanding | 按平台选择后端 | 分别标明仅编译、模拟器运行或真机支持 |

上述顺序是缩小首版范围的建议。跨平台长远目标包含 Windows、Linux、macOS，以及 x86-64、AArch64、RISC-V 64；不暗示这些 OS 与架构的全部组合都需要支持。

验收：同一份可移植应用源码在 M1 两个平台运行；平台差异集中在明确模块中。交叉构建生成的产物必须在目标环境执行，不能仅检查文件存在。

参考：Clang 官方文档明确将 sysroot、目标头文件、库和工具链纳入交叉编译配置。[Cross-compilation using Clang](https://clang.llvm.org/docs/CrossCompilation.html)

### G3：高性能与成本可见

必须能力：

- AOT 原生编译；可控制布局、对齐、栈与堆存储、分配器、值传递和移动。
- 定义泛型、动态分派、闭包捕获、复制和引用计数的成本模型；常用抽象需要有优化结果作为证据。
- 提供向量操作、CPU 特性声明、必要的 intrinsics 和可审查的优化选项。
- 在受支持的调用关系内检查“禁止堆分配”等限制，涵盖隐式分配和析构路径；外部代码的效果摘要必须作为明确的信任边界。
- 可以输出 IR、汇编及必要的优化诊断，支持源级调试与性能分析。
- 定义默认浮点语义与 fast-math 的显式启用方式。CPU/GPU 浮点允许差异和误差范围必须有文档，不能默认承诺位一致。

首版至少覆盖连续数组数值计算、解析/编码、arena 中的图结构修改，以及多线程批处理四类工作负载。算法、数据布局、输入、安全检查与浮点选项必须等价。

性能指标包括吞吐量、延迟分布、峰值内存、分配次数、代码大小和编译耗时。吞吐量较好的平均值不能掩盖严重的尾延迟或单例退化。

初始建议门槛：预先固定的一组 CPU 基准，以耗时比计算的几何平均值不超过优化 C++ 基线的 1.10 倍；单项超过 1.25 倍需列为待解决项或显式记录例外。该门槛是待校准的项目目标，不是语言已有能力或通用性能保证。GPU 和并发性能使用单独基线。

### G4：C 与汇编互操作

必须能力：

- 双向 C ABI：调用 C 函数、向 C 导出函数，支持普通结构体、指针、数组、函数指针、回调、静态库及动态库。
- 从 C 头文件生成受支持范围内的声明，并为导出接口生成 C 头文件；固定解析时的目标、宏及编译选项。
- 定义调用约定、符号可见性、布局、分配/释放配对、回调存活期与线程要求；不能从裸指针签名自动推断出可靠的所有权保证。
- C 接口之外的语言内部 ABI 可以在实验阶段演进，不把内部 ABI 稳定性与 C ABI 兼容混为一谈。
- 支持外部汇编文件和受约束的内联汇编。输入、输出、寄存器破坏、内存效果及架构需求必须表达清楚。
- 失败、panic 或异常不允许未经约定跨过 FFI 边界；按接口转换成错误码或其他明确结果。

首版 C 范围以常见 C11 头文件为起点。位域、特殊打包、复杂宏、变参和编译器扩展必须列入支持清单：未支持项明确拒绝或通过 C 包装函数接入，不能猜测布局。完整支持程度由 ABI 验收逐步扩展。

验收：同一测试库由 C 和本语言互相调用，包含结构体传参/返回、回调及跨边界创建释放；覆盖 M1 的 ABI。汇编路径与可移植实现比较结果，错误架构和错误约束得到诊断。

参考：LLVM 的内联汇编模型包含操作数约束及副作用信息，只有汇编文本不足以描述优化器需要知道的行为。[LLVM Language Reference](https://llvm.org/docs/LangRef.html#inline-assembler-expressions)

### G5：AI 友好与可维护性

必须能力：

- 语法规则一致，格式化确定，公共接口明确；编译器、文档和标准库 API 使用一致的版本信息。
- 提供机器可读诊断：稳定错误码、源范围、相关声明、约束冲突原因；能够提供反例或修复建议时再提供，不能编造验证结果。
- 语义查询至少覆盖符号、类型、引用、调用关系、目标能力和受支持的效果信息；不要求 AI 靠正则恢复全部语义。
- 快速局部检查和增量构建；固定工作负载测量 p50/p95 响应时间，避免只报告完整编译时间。
- 契约、边界测试及性能基线可单独审查。工具区分实现修改与规格修改，不能把删除检查或放宽需求当作修复成功。
- 生成的 C 绑定、Shader 绑定和跨平台条件分支具有源码关联与可审查差异。

验收：准备新增功能、跨文件重构、FFI 修复、并发错误修复、Shader 布局变更五类保留任务，使用固定模型、上下文、工具权限、时间和推理预算，与使用成熟工具的 C++/Rust 对照。统计成功率、人工介入、遗漏缺陷、检查轮数及性能回退。

公开语言说明和范例，但保留验收用例；新语言的学习成本计入结果。首版首先提供完整测量流程，是否“更适合 AI”必须由实验结果支持，不能由命名或语法简短程度决定。

### G6：图形学与 Shader

必须能力：

1. 用本语言编写 vertex、fragment、compute 入口。首版至少有一条实际 GPU 执行路径，只有导入外部 Shader 不算完成。
2. CPU 与 GPU 共用兼容的语法、模块、数值类型和可移植函数；编译器区分执行域，检查从入口可达的全部调用。
3. GPU 基础类型包括向量、矩阵、纹理、采样器、buffer 视图及访问权限；向量类型不能机械地等同于 CPU SIMD 寄存器布局。
4. 描述地址空间、Shader 阶段、workgroup、必要的原子与 barrier 语义。拒绝不受支持的递归、分配、主机调用和不合法的同步位置。
5. 共享数据布局需要显式约定：字段偏移、对齐、矩阵约定、数组步长和允许的字段类型。普通 CPU 对象不自动成为可直接上传的 GPU 数据。
6. 从同一份接口描述生成主机布局和资源绑定信息，检查 Shader 与主机接口是否匹配；布局变更必须触发依赖重建和兼容性检查。
7. 为 GPU 特性定义能力集合：基础可移植集合与平台扩展分开检查，缺失能力早期报错。
8. 提供最小的安全 GPU 资源封装：提交、完成事件及资源存活关系可追踪。释放主机句柄不能导致仍在执行的 GPU 工作使用已释放资源。

Shader 产物和运行环境：

| 目标路线 | 典型产物 | 执行环境 | 建议阶段 |
| --- | --- | --- | --- |
| Vulkan | SPIR-V | Vulkan 驱动 | M1 |
| Direct3D 12 | DXIL | D3D12 驱动 | M2 或后续 |
| Metal | MSL，配合平台工具生成 Metal library | Metal | M2 |
| WebGPU | WGSL，配合运行时后端 | 浏览器或原生 WebGPU 实现 | 后续 |

这些格式并非同一层级。生成 Shader 代码不等于已经具备对应图形 API 的主机运行库、SDK 和平台测试。

验收必须超过三角形：完成一个纹理网格绘制及一个 GPU compute 任务；执行读回与参考结果比较；覆盖结构体 padding、矩阵、数组、绑定类型错误和异步释放。数值任务按声明的精度比较，整数精确任务可要求逐值一致。至少在两种实际 GPU 实现上运行基础用例，分别记录平台与驱动；离线验证或软件实现不替代全部真机验收。

普通 Shader 不承诺任意 CPU 功能可用；GPU 写入竞争与 CPU 线程安全的保证分别说明。对非法索引要规定拒绝、受保护访问或其他明确定义的行为，不能默默依赖未验证的驱动行为。

可以使用 Slang 等成熟组件辅助后端，但本语言前端必须拥有一致的检查规则、接口描述和诊断定位。Slang 的能力检查设计可供参考；WGSL 规范也说明了地址空间与共享布局约束的重要性。[Slang capabilities](https://shader-slang.org/slang/user-guide/capabilities)；[Slang targets](https://shader-slang.org/slang/user-guide/targets)；[WGSL specification](https://www.w3.org/TR/WGSL/)

### G7：多线程与并行

必须能力：

- 系统线程、join、锁、条件变量、原子操作及明确的 CPU 内存模型。
- 作用域任务、显式任务池和基础数据并行。共享状态的读写规则与所有权模型一致。
- 作用域退出、失败和取消时明确子任务完成与清理规则。取消为协作式时必须明确，不能承诺任意代码即时终止。
- 捕获的引用不能超出有效期；独立任务只接收满足跨线程要求的数据。
- 原子内存序具有规范和目标映射。要求 lock-free 的操作在目标不支持时应拒绝或要求显式选择回退，不能隐藏引入锁。
- 为任务命名和追踪提供接口；多线程错误能关联到创建点与任务来源。

首版以 CPU 并行为重点；完整异步 I/O 生态后置。CPU 线程同步与 GPU 执行/内存同步采用分别定义的规则。

验收：编译期拒绝非法共享写入、逃逸借用和错误线程传递；运行时检查错误传播、取消、收尾与资源存活。对粗粒度并行任务在 1/2/4/8 线程上测量扩展性，并与同算法的成熟实现比较；不要求所有任务线性加速。

作用域并发可以参考 Rust 已有设计，避免为“新语言”重复发明缺乏依据的生命周期规则。[Rust scoped threads](https://doc.rust-lang.org/std/thread/fn.scope.html)

## 4. 首版整体验收项目

建立一个小型跨平台图形计算程序，串联所有目标：

1. 通过清单取得一个固定版本 C 库，完成资源解析或解码。
2. 通过作用域任务并行准备网格或图像数据。
3. 对热点提供 SIMD 或内联汇编实现，并验证可移植回退。
4. 使用本语言编写 vertex、fragment 和 compute Shader。
5. 使用共同接口描述传递数据，执行 compute、绘制、读回与结果验证。
6. 退出或取消时正确等待任务与 GPU 工作，并回收资源。
7. 同一源码与锁定输入在 Linux/Windows 完成构建和运行；具备完整依赖时离线构建。
8. 让 AI 完成一次跨主机/Shader 的结构布局修改，再完成一次并发重构；保留独立的正确性与性能验收。

另保留一个非图形的 IR 图修改程序，验证语言没有因图形样例而忽略系统程序中的交叉引用、删除与批量更新问题。

## 5. 实现阶段与完成条件

| 阶段 | 必须交付 | 完成条件 |
| --- | --- | --- |
| M0 语义原型 | 值与资源规则、模块与错误语义、CPU/GPU 执行域草案；Linux CPU 程序；基础 C ABI；Shader 子集试编译 | 能表达代表性程序，明确主要语义矛盾；不得称为完成七项目标 |
| M1 七项最小闭环 | 双平台运行、固定依赖构建、原始指针模型、C/汇编、诊断与查询、三类 Shader、作用域并行 | 整体验收项目运行；应拒绝用例确实被拒绝；公布限制与性能数据 |
| M2 平台与工程扩展 | ARM64/macOS、Metal 等后端、增量与调试改善、异步 I/O、更多原生依赖 | 扩展支持矩阵，回归既有语义和性能 |
| M3 稳定化 | 语言版本迁移、长期兼容策略、RISC-V 等目标、成熟发布流程 | 按项目需求制定，不预先承诺日期 |

依赖管理的输入模型、CPU/GPU 能力模型以及原始内存模型从 M0 开始设计。实现可以分阶段，接口上不能把这些能力留作无法兼容的事后补丁。

## 6. 冲突时的决策原则

- 正确性与性能：优先改善表达方式、布局和优化，并通过检查级别让运行时验证成本保持显式。
- 可移植性与特定硬件性能：提供可移植基础能力和显式专用路径，并验证回退。
- 主机/Shader 统一与执行模型差异：共享兼容部分，拒绝不适用的调用，明确数据转换及同步成本。
- AI 自动修复与规格保持：修复实现时保持已确认的验收要求；规格变化单独展示和审查。
- 功能丰富与实现可控：保留可运行的端到端路径，延后后端数量与高级特性，不用空 API 替代基本能力。

## 7. 下一轮需要形成的设计决策记录

无需先决定语言名字和全部语法。应先针对代表性代码确定：

1. 主要所有权/借用模型及 arena、稳定句柄的表达；
2. CPU 与 GPU 的效果、能力、布局和执行域规则；
3. 错误、取消、panic 与资源清理语义；
4. C ABI 支持范围、目标平台及 M1 GPU 基础能力集合；
5. 模块接口、泛型与编译缓存边界；
6. 可复现构建记录和 AI 验收任务协议。

每项决策记录问题、候选方案、取舍、反例、验收方式及是否可以后续兼容修改。原型基准运行前冻结比较协议；数据用于修订目标，不用于倒推隐藏掉失败项目。
