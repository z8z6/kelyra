我对 Kelyra 的建议很明确：**语法应当保守、规则应当激进地统一**。

也就是说，外观保持 C/Rust/Zig 程序员熟悉的形式，但彻底去掉 C++ 的历史包袱、解析歧义和多种等价写法。

## 推荐的总体风格

可以概括为：

* C/Go 风格的代码块
* 模式匹配和显式错误传播
* Zig 风格的编译期能力与底层控制
* WGSL 风格的 Shader 属性和地址空间
* Swift 风格的可读声明，但不要引入过多语法糖

```kly
module example.renderer;

import std.fs;
import gpu.{Buffer, Device};

pub struct Vertex {
    position: vec3[f32],
    normal: vec3[f32],
}

pub fn load_mesh(path: str) -> Result[Mesh, LoadError] {
    let bytes = fs.read(path)?;
    return Mesh.decode(bytes);
}
```

## 1. 坚持“名称在左，类型在右”

不要继承 C/C++ 声明语法。

```kly
let count: i32 = 10;
var position: Vec3[f32];
const max_lights: usize = 128;

fn distance(a: Vec3[f32], b: Vec3[f32]) -> f32 {
    return length(a - b);
}
```

避免：

```cpp
const char* const* names;
int (*callback)(float);
```

Kelyra 对应形式应该是：

```kly
let names: **char;
let callback: fn(f32) -> i32;
```

这会极大降低 parser、IDE、错误诊断以及 AI 生成代码的难度。

## 2. 泛型使用方括号

我不推荐沿用 C++、Rust 的 `<T>`：

```kly
struct Vec[T] {
    data: *T,
    length: usize,
}

fn max[T: Ord](a: T, b: T) -> T {
    return if a > b { a } else { b };
}
```

方括号有几个好处：

* 不会和 `<`、`>` 运算符冲突
* 不需要处理 C++ 的 `>>` 历史问题
* Pratt Parser 不必猜测当前是比较表达式还是泛型参数
* 对人和 AI 都更容易识别

Rust 泛型语法中存在一些必须依靠额外括号或语法限制解决的解析问题，这正是新语言可以绕开的地方。[Rust Reference](https://doc.rust-lang.org/reference/items/generics.html)

常量泛型也应显式区分：

```kly
struct Matrix[T: Float, const Rows: usize, const Cols: usize] {
    values: Array[T, Rows * Cols],
}
```

## 3. 变量和指针保持简单

```kly
let x = 10;
x = 20;
```

Kelyra 不使用 `mut` 关键字，也不区分可变和不可变指针。`&` 是取地址运算符，`*` 同时用于指针类型和解引用：

```kly
fn modify(value: *Data);

let value: Data;
let pointer: *Data = &value;
*pointer = replacement;
```

指针不携带所有权、借用或生命周期语义。

## 4. 语句分号必须明确

建议：

* 普通语句必须有分号
* 块、函数、类型声明后不加分号
* 换行不参与语法

```kly
let x = calculate();
process(x);

if x > 0 {
    log("positive");
}
```

这比自动分号插入更稳定，也更适合代码生成、格式化和宏展开。

块可以是表达式：

```kly
let category = if score >= 90 {
    "excellent"
} else {
    "normal"
};
```

但我建议 v0.1 中函数返回仍优先使用显式 `return`，避免过早引入“最后一个表达式是否有分号改变语义”的陷阱。

## 5. 使用代数数据类型和模式匹配

```kly
enum Shape {
    Circle { radius: f32 },
    Rectangle { width: f32, height: f32 },
    Empty,
}

fn area(shape: *Shape) -> f32 {
    return match shape {
        Shape::Circle { radius } =>
            pi * radius * radius,

        Shape::Rectangle { width, height } =>
            width * height,

        Shape::Empty =>
            0.0,
    };
}
```

建议规定：

* `::` 用于模块、类型、枚举成员
* `.` 只用于实例成员
* `match` 默认要求穷尽
* `_` 明确表示忽略
* 不允许隐式 fallthrough

## 6. 错误使用 `Result`，不默认使用异常

```kly
enum FileError {
    NotFound,
    PermissionDenied,
    InvalidData,
}

fn read_config(path: str) -> Result[Config, FileError] {
    let bytes = fs.read(path)?;
    let config = Config.parse(bytes)?;
    return Ok(config);
}
```

建议：

* `Result[T, E]` 表示可恢复错误
* `?` 只负责错误传播
* `panic` 只用于不可恢复错误
* 不在 v1 中加入隐式异常和栈展开语义
* 错误集合必须可以被文档工具和 IDE 查询

Zig 的 error union 证明了语言级错误类型对于静态分析、文档和优化很有价值；但 Kelyra 可以使用更明确的 `Result[T,E]`，减少符号密度。[Zig Language Reference](https://ziglang.org/documentation/master/)

## 7. 属性统一使用 `@`

所有编译器属性、FFI、Shader 接口都用同一种形式：

```kly
@layout(c)
pub struct CVertex {
    x: f32,
    y: f32,
}

@inline(always)
fn fast_abs(x: f32) -> f32 {
    return if x < 0.0 { -x } else { x };
}

@deprecated("use new_api")
fn old_api();
```

不要同时出现：

* `[[attribute]]`
* `__attribute__((...))`
* `__declspec(...)`
* `#pragma`
* 特殊注释

布局也必须显式。Rust 同样使用类型属性区分默认布局与 C 布局，说明“内存表示不能只靠直觉推断”。[Rust Type Layout Reference](https://doc.rust-lang.org/stable/reference/type-layout.html)

## 8. C FFI 应当是一等语法

```kly
extern "C" {
    fn malloc(size: usize) -> *void;
    fn free(ptr: *void);
}

@export("kelyra_initialize")
extern "C" fn initialize(config: *CConfig) -> i32 {
    return 0;
}
```

C 函数和原始指针可以直接使用；正确性由程序员负责。

内联汇编使用结构化操作数，见 [`asm` 设计](../asm.md)。不直接复制
GCC 内联汇编的约束字符串体系。

## 9. Shader 使用同一语言子集

```kly
struct Camera {
    view_projection: mat4x4[f32],
}

@group(0)
@binding(0)
var camera: uniform Camera;

@vertex
fn vertex_main(
    @location(0) position: vec3[f32],
    @location(1) normal: vec3[f32],
) -> @builtin(position) vec4[f32] {
    return camera.view_projection * vec4(position, 1.0);
}

@fragment
fn fragment_main(
    @location(0) normal: vec3[f32],
) -> @location(0) vec4[f32] {
    return vec4(abs(normal), 1.0);
}
```

Shader 不应该成为另一套完全不同的语法，而应当是 Kelyra 的受限执行配置：

```kly
target shader {
    forbid heap;
    forbid recursion;
    forbid exceptions;
}
```

WGSL 已经验证了 `@vertex`、`@binding`、`@location` 这类结构化属性非常适合描述 GPU 接口。[WGSL Specification](https://www.w3.org/TR/WGSL/)

## 10. 并发语法应该体现结构化并发

```kly
fn update(world: *World) -> Result[Frame, Error] {
    return scope {
        let physics = spawn simulate(world);
        let visibility = spawn cull(world);

        let state = await physics;
        let visible = await visibility;

        return build_frame(state, visible);
    };
}
```

关键约束是：

* `spawn` 出来的任务不能无意逃出 `scope`
* `scope` 退出前自动等待或取消子任务
* detached task 必须使用显式 API

`async fn` 可以保留，但不要让 `async` 成为所有并发的核心；数据并行、线程和异步 I/O 是不同问题。

## 11. 限制运算符和重载

建议 v1：

* 运算符优先级完全固定
* 不允许用户定义新运算符
* 不允许用户定义优先级
* 运算符重载只能通过标准 trait
* 禁止逗号运算符
* 禁止隐式布尔转换
* 赋值不是普通值表达式

```kly
trait Add[Self, Rhs = Self] {
    type Output;
    fn add(self: Self, rhs: Rhs) -> Output;
}
```

这样 Pratt Parser 可以使用一张静态 binding-power 表完成绝大多数表达式解析。

## 12. 不要在 v1 引入传统文本宏

避免：

```c
#define max(a, b) ...
#include "header.h"
#ifdef WINDOWS
```

优先提供：

```kly
comptime fn generate_table(size: usize) -> Array[u32, size] {
    // 编译期执行
}

const table = comptime generate_table(256);
```

以后若加入宏，应该满足：

* 卫生宏
* 操作 token tree 或 AST
* 输入输出可以检查
* 展开结果可以被 IDE 获取
* 有递归与资源限制

## 13. 为 AI 友好设定语法硬规则

AI 友好并不是增加自然语言语法，而是让代码尽量只有一种标准写法：

* 一个概念只保留一种主要语法
* 禁止依靠缩进改变语义
* 禁止隐式声明
* 禁止 C++ ADL 一类非局部查找
* 尽量减少上下文关键字
* 不允许任意预处理器修改 token 流
* 类型和模块路径明确
* formatter 由官方提供，输出唯一规范格式
* AST 节点具有稳定名称和 source span
* 编译器能输出结构化 JSON 诊断
* 错误恢复必须是 parser 的正式设计目标

## 建议的 v0.1 语法范围

第一版只实现：

1. `module`、`import`
2. `let`、`var`、`const`
3. `fn`
4. `struct`、`enum`
5. `if`、`while`、`for`、`match`
6. `return`、`break`、`continue`
7. 原始指针、数组和函数类型
8. `Result[T,E]` 与 `?`
9. `extern "C"`
10. 基础 `@attribute`
11. 固定运算符集合
12. 泛型语法先解析，语义可以稍后实现

暂时不要加入：

* 类继承
* 隐式构造
* 函数重载
* 默认参数
* 用户自定义运算符
* token 宏
* 可变参数泛型
* 异常
* 复杂闭包捕获规则

一句话总结：**Kelyra 应该让代码的能力很强，但让每一行代码的解释非常单一。** 这比创造全新的标点体系，更可能形成长期生命力。
