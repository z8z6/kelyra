先说结论：**几乎不存在“其他语言理论上做不到”的单一特性**。真正的机会是利用 Kelyra 没有历史包袱，把其他语言只能依靠库、宏、构建脚本和外部工具勉强拼接的能力，统一成一种编译期语义。

我认为 Kelyra 最有潜力形成的核心定位是：

> **每个函数都具有机器可理解的执行契约：它会做什么、在哪里运行、使用哪类内存、需要哪些硬件能力，以及能否跨 ABI。**

这比“更简洁的 C++”更具有独特性。

## 第一优先级：执行契约系统

传统函数类型只描述输入和输出：

```kly
fn process(data: Slice[f32]) -> Result[Image, Error];
```

Kelyra 可以进一步描述：

```kly
fn process(data: Slice[f32]) -> Result[Image, Error]
    effects { alloc(arena), parallel }
    requires { simd }
    guarantees { deterministic };
```

建议首批内置 effect：

* `io`
* `alloc(region)`
* `panic`
* `block`
* `parallel`
* `atomic`
* `nondeterministic`
* `ffi`
* `gpu`
* `network`

局部函数可以推导，公开接口建议显式声明。

### 它能解决什么

实时音频函数可以禁止分配、阻塞和锁：

```kly
@realtime
fn audio_callback(buffer: *Slice[f32])
    effects {};
```

Shader 可以禁止 I/O、堆分配和 panic：

```kly
@fragment
fn shade(input: FragmentInput) -> vec4[f32]
    effects {};
```

确定性交易回测可以禁止时钟、随机数和无序原子操作：

```kly
@deterministic
fn evaluate(strategy: *Strategy, data: *MarketData) -> Report;
```

依赖管理器也可以检查：

```toml
[policy]
deny-effects = ["network", "process-spawn"]
```

Koka 已经证明精确 effect type 是可行的，但它不是以底层系统、C ABI、GPU 和包安全策略为中心。[Koka effect types](https://koka-lang.github.io/koka/)

Kelyra 的突破点应当是：**把 effect、目标平台、内存空间和依赖权限连接起来。**

---

## 第二优先级：C 接口语义契约

仅仅导入 C 头文件还不够。C 头文件只能告诉编译器：

```c
void process(const uint8_t* data, size_t size);
```

它没有表达：

* `data` 是否允许为空
* `size` 是否是元素数还是字节数
* 函数是否保留指针
* 返回值由谁释放
* 是否线程安全
* 是否会调用回调
* 失败时如何表示

Kelyra 可以增加独立的 `.kci`，即 Kelyra C Interface Contract：

```kly
contract c.process {
    data: read_only bytes[size];
    data: nonnull if size > 0;
    retains data: false;

    effects { ffi };
    thread_safe: true;
}
```

资源所有权：

```kly
contract c.image_create {
    returns owned ImageHandle;
    destroy_with c.image_destroy;
    failure null;
}
```

导入后自动得到两层接口：

```kly
import c "image.h" as raw_image
    contract "image.kci";

let raw = raw_image.image_create(...);
```

以及惯用包装：

```kly
let image: Image = image.create(...)?;
```

需要注意：编译器可以验证 `.kci` 与头文件的类型、ABI、参数数量是否一致，但无法完全证明外部二进制遵守其行为声明。因此这些契约必须：

* 可审计
* 可签名
* 可由 Sanitizer 动态验证
* 随依赖版本锁定
* 变更时触发兼容性检查

Zig 已经具有很自然的 C 互操作，Carbon 也将 C++ 互操作视为核心目标；仅仅“导入头文件”已经不足以成为长期差异。[Zig C interoperability](https://ziglang.org/documentation/master/#C)、[Carbon interoperability goals](https://github.com/carbon-language/carbon-lang/blob/trunk/docs/design/interoperability/philosophy_and_goals.md)

**从 ABI 兼容继续推进到语义契约兼容**，才可能成为 Kelyra 的独特能力。

---

## 第四优先级：原生协议状态类型

很多系统对象不是“具有一些方法的对象”，而是状态机：

* 文件：关闭 → 打开 → 关闭
* Socket：创建 → 绑定 → 监听 → 接收
* GPU Command Buffer：初始 → 录制 → 可提交 → 已消费
* TLS：未连接 → 握手 → 已连接
* 数据库事务：活动 → 提交或回滚

Rust 可以用 typestate 泛型模拟，但会产生大量泛型状态、`PhantomData` 和包装类型。Kelyra 可以把它变成语言原生概念：

```kly
protocol CommandBuffer {
    state Initial;
    state Recording;
    state Ready;
    state Submitted;

    transition begin(self: Initial) -> Recording;
    fn draw(self: *Recording, mesh: *Mesh);
    transition end(self: Recording) -> Ready;
    transition submit(self: Ready) -> Submitted;
}
```

使用时不需要显式写状态参数：

```kly
var commands = device.create_commands(); // Initial

commands.begin();                         // Recording
commands.draw(&mesh);
commands.end();                           // Ready
queue.submit(move commands);              // Submitted

commands.draw(&mesh);
// 编译错误：commands 已经提交，并且当前不是 Recording 状态
```

这对图形学尤其有价值，可以在编译期排除大量 Vulkan/D3D12 使用错误。

同样也能包装 C API：

```kly
protocol SqliteStatement {
    state Prepared;
    state Row;
    state Done;
    state Finalized;
}
```

## 第五优先级：统一 CPU、SIMD、GPU 和 Shader 的执行模型

“能写 GPU”本身已经不独特，Mojo 等语言也明确面向 CPU、GPU 和加速器。[Mojo documentation](https://docs.modular.com/mojo/)

Kelyra 应追求更强的目标：

> 同一个算法只写一次，编译器根据执行契约生成标量、SIMD、多线程、GPU 和 Shader 版本，并验证不同后端的语义差异。

```kly
@portable(cpu, simd, gpu)
fn transform(
    input: ReadBuffer[Vec4],
    output: WriteBuffer[Vec4],
    matrix: Mat4,
) {
    parallel for i in 0..input.len {
        output[i] = matrix * input[i];
    }
}
```

编译器可以生成：

* CPU 标量循环
* AVX2/AVX-512/NEON/RVV
* 多线程 CPU 任务
* CUDA/HIP/SPIR-V/Metal kernel
* Vulkan Compute Shader

但不是所有函数都可以跨目标，所以应使用能力约束：

```kly
fn algorithm[T: ComputeTarget](
    target: T,
    data: Buffer[f32, T.memory],
) where
    T.supports[f32],
    T.supports[atomic_add];
```

### 内存空间属于类型系统

```kly
let host: Buffer[Vertex, memory.host];
let pinned: Buffer[Vertex, memory.pinned];
let device: Buffer[Vertex, memory.gpu];
let shared: Buffer[Vertex, memory.shared];
```

拷贝必须明确：

```kly
let device = copy host -> memory.gpu;
```

但编译器可以进行生命周期分析并消除不必要的传输。

这会比单纯提供 `@gpu` 属性更有价值，因为它统一解决：

* 地址空间
* 生命周期
* 异步传输
* 同步屏障
* kernel 能力
* 跨硬件特化

## 第六优先级：确定性并发作为语言保证

传统“线程安全”只保证不出现数据竞争，不保证结果可以复现。

Kelyra 可以区分两种并发：

```kly
parallel deterministic {
    // 结果与调度顺序无关
}
```

以及：

```kly
parallel nondeterministic {
    // 允许竞争式工作窃取、无序原子更新等
}
```

确定性函数禁止：

* 读取墙上时钟
* 隐式随机数
* 未排序的并行浮点归约
* 依赖调度顺序的原子更新
* 遍历无稳定顺序的容器
* 未声明的外部 I/O

```kly
@deterministic
fn sum(values: Slice[f64]) -> f64 {
    return parallel_reduce(
        values,
        identity = 0.0,
        order = reduction.tree_fixed,
        operation = add,
    );
}
```

这对以下场景极有吸引力：

* 交易回测
* 游戏逻辑
* 物理仿真
* 编译器
* 分布式计算
* 测试和故障复现

进一步还可以生成最小重放日志：只记录真正的外部非确定性输入，而不是记录所有线程调度。

## 第七优先级：布局代数

现在不同生态拥有各自布局规则：

* C ABI
* packed 二进制协议
* 网络字节序
* Vulkan `std140/std430`
* Metal buffer layout
* 磁盘格式
* SIMD vector layout

Kelyra 可以把布局本身变成可查询、可比较的编译期对象：

```kly
@layout(c)
struct CHeader {
    kind: c.uint,
    size: c.size,
}

@layout(wire, endian = little, padding = none)
struct PacketHeader {
    version: bits[4],
    kind: bits[4],
    length: u16,
}

@layout(gpu.std430)
struct GpuParticle {
    position: vec3[f32],
    mass: f32,
}
```

编译器提供：

```kly
comptime {
    assert layout[CHeader].compatible_with[c.CHeader];
    assert sizeof[GpuParticle] == 16;
    assert offset_of[GpuParticle.mass] == 12;
}
```

类型转换分为：

```kly
bitcast[A, B](value);       // 仅布局完全兼容
convert[A, B](value);       // 编译器生成字段转换
serialize[wire](value);     // 显式序列化
```

每个公开类型都有布局指纹：

```text
API hash:     92e80...
ABI hash:     f671b...
Layout hash:  207ad...
```

这样包管理器可以准确判断一次升级究竟是：

* 源码兼容
* API 兼容但 ABI 不兼容
* 完全 ABI 兼容
* 仅特定目标兼容

## 第八优先级：原生稳定组件与热重载

动态库 ABI 和热重载不应该完全交给构建脚本与手工约定。

```kly
component Renderer @abi(version = 3) {
    export fn create(device: *Device) -> Renderer;
    export fn render(self: *Renderer, frame: *Frame);
    export fn destroy(self: Renderer);
}
```

升级状态迁移：

```kly
migrate RendererState from version 2 to version 3 {
    return RendererState {
        camera: old.camera,
        exposure: 1.0,
    };
}
```

编译器负责：

* 稳定符号
* ABI 兼容性检查
* 接口表
* 状态版本
* 动态库加载器
* 热重载安全点
* 旧版本兼容适配器

这对于游戏引擎、图形工具、插件系统和长期运行服务具有明显吸引力。

## 第九优先级：真正 AI 友好的语义接口

不要把“AI 友好”设计成自然语言关键字，也不要把 LLM 塞进编译器。

正确方向是让编译器成为可查询的语义服务器。

### 类型洞

```kly
fn build_pipeline(device: *Device) -> Pipeline {
    let layout: PipelineLayout = ?layout;
    return ?pipeline;
}
```

编译器返回：

```json
{
  "hole": "layout",
  "required_type": "PipelineLayout",
  "available_values": ["device", "default_layout"],
  "allowed_effects": ["alloc"],
  "forbidden_effects": ["io", "ffi"],
  "ownership_constraints": []
}
```

AI 根据精确约束补代码，而不是只根据文本猜测。

### 语义补丁

AI 不直接说“替换第37到51行”，而是提交：

```json
{
  "operation": "replace_expression",
  "node_id": "expr:98ac21",
  "expected_type": "Result[Pipeline, Error]",
  "new_ast": {}
}
```

编译器验证：

* AST 节点仍然存在
* 类型正确
* 所有权正确
* effect 未扩大
* ABI 未改变
* 测试覆盖哪些路径

### 意图约束

```kly
fn binary_search[T: Ord](
    values: Slice[T],
    target: *T,
) -> Option[usize]
    requires sorted(values)
    ensures result.is_none()
         || values[result.unwrap()] == *target;
```

这些约束可以分别用于：

* Debug 检查
* 属性测试生成
* 模糊测试
* AI 代码生成
* 优化
* 静态证明

AI 的输出仍必须通过普通编译器，而不是获得特殊豁免。

## 我最推荐的 Kelyra 核心组合

不要同时把九项都作为 v0.1 目标。我建议形成三层核心：

### Kelyra v0.1

1. 一等 C ABI
2. Clang 头文件导入
3. 基础 effect 推导
4. 内存空间进入类型系统
5. 结构化并发
6. 机器可读诊断和稳定 AST

### Kelyra v0.5

1. `.kci` C 语义契约
2. 原生 protocol/typestate
3. CPU/SIMD/GPU 统一 kernel
4. 布局代数和 ABI 指纹

### Kelyra v1.0

1. 确定性并发
2. 稳定组件 ABI
3. 热重载和状态迁移
4. 完整语义编辑协议
5. typed holes 与契约驱动生成

## 最值得押注的两个特性

如果资源有限，我会押注：

1. **C 语义契约**
2. **统一 effect、执行目标和内存空间的执行契约系统**

第一项会让 Kelyra 更自然地使用庞大的 C 生态；第二项会让它从普通 CPU 程序扩展到实时、多线程、SIMD 和 GPU。

两者结合后的定位非常清晰：

> **Kelyra：能够继承 C 生态，并用同一套执行语义覆盖 CPU、并发和 GPU 的原生系统语言。**

这比单纯宣称“更快、更现代的 C++”更难被现有语言复制。
